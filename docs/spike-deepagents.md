# deepagents 迁移评估（spike）

> 目的：在**不改动生产代码**的前提下，验证两件事——
> 1. deepagents 的「看状态 → 选工具」能力，是否比现有规则+自研循环更能覆盖长尾说法
> 2. 它的人机确认（`interrupt_on`）能否桥接我们现有的确认卡
>
> 运行：`cd backend; python scripts/deepagent_spike.py`
> 全部工具为**干跑**，不会提交 ComfyUI。

## 结论

| 维度 | 结果 | 判断 |
|---|---|---|
| 工具选择（10 条真实语句） | **9/10** | 明显优于「为每句话写规则」 |
| 单条延迟 | 4.3 ~ 10.7s（均值 ≈6.6s） | 与现有自研循环（4~15s）持平，可接受 |
| 先查状态再行动 | 10/10 都调了 `describe_state` | **这正是我们最缺的**：它不再猜「刚才那个」是哪张 |
| 确认门 | `paused=true, interrupt_count=1` | **可桥接**，`interrupt_on` 直接能停 |
| 唯一失败 | 「生化危机」→ 反问要什么 | 行为差异，可通过系统提示要求「题材先扩写再出片」修正 |

## 关键发现

1. **它的优势不是"更会聊"，是"会先查"**。10 条里有 10 条先 `describe_state`，
   包括「视频啊」「把刚才那张图塞进第二镜当首帧」这种最依赖上下文的说法——
   而我们现在的实现是靠 `last_asset_id`、`last_topic` 一个个补字段。

2. **确认门没有想象中难**。`interrupt_on={"make_image": True}` 直接让图在工具调用前暂停，
   返回的 task 上带着 interrupt 载荷，可以渲染成我们现在的确认卡。

3. **风险仍在事件层**，不在决策层。我们前端吃的是自定义 SSE（thinking/tool_call/step/
   message_delta），deepagents 走 LangGraph 流，形状不同——这块要写桥接，不是改决策。

4. **状态脏的问题它不会自己解决**。spike 第一次跑时我的假上下文和工具返回不一致，
   它立刻停下反问——这是对的行为，但也说明：**状态喂错了，agent 只会更谨慎地停住，
   不会神奇地猜对**。

## 迁移建议（如果决定换）

| 步骤 | 内容 | 估时 | 风险 |
|---|---|---|---|
| 1 | 五个只读工具 + 十个动作工具包成 LangChain tool（干跑可复用） | 1 天 | 低 |
| 2 | 用 deepagents 替换 `decide/planner`，**保留高频快通道** | 1 天 | 中 |
| 3 | `interrupt_on` → 现有确认卡（pending 载荷字段对齐） | 1~1.5 天 | **高** |
| 4 | LangGraph 事件 → 现有 SSE 契约（thinking/tool_call/step） | 1 天 | 中 |
| 5 | 回归：34 条语料 + 场景测试 + 20 条未见说法 | 1 天 | 低 |
| 合计 | | **5 天左右** | |

**建议的验收线**：现有 34 条语料不低于 31/31；另备 20 条**没写进规则**的说法，
deepagents 版至少 16/20 正确（现有规则版预计明显低于此）。

## 还没验证的

- 多步计划（「三镜短片」这种）：spike 只跑了单步，deepagents 的 planning middleware 未测
- 子 agent 分工：未测
- 长会话（>20 轮）下的上下文与成本：未测
- 真实出图/出视频链路：全部干跑
