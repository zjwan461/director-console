# Step 2 评估：从「单意图分发」到「工具循环」

日期：2026-10-26　前提：Step 1（产物列表 + 指代 + 修订）已上线，30 条语料 30/30。

---

## 一、实测：当前架构的边界在哪

用 6 条真实风格的复合请求打当前实现（只到确认卡，不执行）：

| 输入 | 实际结果 | 期望 |
|---|---|---|
| 画一张雪夜黑猫，然后做成 5 秒视频，再配一段旁白 | `action=video`（只做了视频） | 出图 → 视频 → 旁白 三步 |
| 把这张图做个竖屏视频，8 秒，加点雪 | `action=video`（参数对，但"加点雪"没进 prompt） | 视频 + prompt 补充 |
| 先出两张不同角度的剑客，我挑一张 | `action=image`（只出一张） | 2 张候选 |
| 这个片子整体节奏再快一点，BGM 换成轻快的 | `action=bgm`（节奏没改） | 调速 + 换 BGM |
| 把第二个镜头改成夜里，然后把片头改成《归人》 | `done`，回复"这次会话只有 1 个产物" | 改镜头 + 改片头 |
| 刚才那张太暗了，重来一版，但保持同样的构图 | `action=image`（当成重新生成，没复用构图） | 修订版 |

**结论**：单意图架构在「一句话一件事」上很准，在**一句话多件事**上必然丢动作。
这不是规则写得不够多，而是**动作空间是单选**。

另有两个已暴露的具体缺口：

1. `太暗了` 不在亮度词表里（只有 `暗一点/更暗/压暗/暗些`）——规则穷举必然漏
2. `第二个镜头` 被解析成产物 #2，而不是镜头的第 2 个——"个"和"镜"混用

## 二、三个选项的取舍

| | 做法 | 解决什么 | 不解决什么 | 成本 | 风险 |
|---|---|---|---|---|---|
| **A** | 继续加规则（多意图切分 + 更多词表） | 部分复合句 | 长尾永远漏；规则继续膨胀 | 1-2 天 | 每加一条规则都在制造新冲突（本轮已修 3 次） |
| **B** | LangGraph 上做工具调用循环（ReAct），保留确认门 | 多意图、长尾、参数补充 | 跨会话长期规划 | 3-4 天 | 每步一次模型调用，推理模型很慢 |
| **C** | deepagents 当外层规划器，现有图当子 agent | 多镜创作、长任务分解 | 单句问答（用不上） | 5-7 天 | 依赖年轻、调试困难、token 成本高 |

**建议：先 B，用数据决定要不要 C。**

理由：

- 上表 6 条里 5 条是"多动作"，这是**编排问题**，不是规划问题；B 就能解
- C 的价值在"三镜短片、先挑图再配乐"这种**跨多步的创作流程**，等 B 上线后再看还有多少 B 解不了
- 继续 A 是负收益：本轮为了让规则不打架，已经重排了三次优先级

## 三、Step 2 设计（若采用 B）

### 3.1 工具清单（把现有能力显式化）

| 工具 | 入参 | 是否需要确认 |
|---|---|---|
| `make_image` | prompt, aspect, megapixels | 是（花钱） |
| `make_video` | prompt, mode, duration, aspect, image_ref | 是 |
| `revise` | target_ref, patch | 是 |
| `lookup_assets` | kind, q | 否 |
| `export_film` | quality | 是 |
| `polish_film` | kinds, tts, titles | 是 |
| `set_bgm` | mode, query | 是 |
| `set_film_options` | transition, title, tail, aspect | 是 |
| `create_project` / `add_shots` | name / prompts | 是 |
| `describe_state` | — | 否（给模型看"现在有什么"） |

### 3.2 循环

```text
规则快速通道（保留）
  ↓ 命中就不进循环（仍是 0.5s）
decide
  ↓
plan: [{tool, args}, ...]        # 一次给出多个动作
  ↓
逐个 confirm（interrupt）→ 执行
  ↓
每步结果回填 state，最多再规划一次（最多 4 步）
```

关键：**确认门不交给模型**。模型只负责"调什么、按什么顺序"，是否执行仍由用户点。

### 3.3 延迟控制（最大的风险）

推理模型单次 2 分钟，4 步就是 8 分钟，不可接受。三条硬约束：

1. **规则通道不动**：常见单句仍然 0.5s，不进循环
2. **规划只调用一次**：一次拿到动作数组，而不是"每一步都问模型"
3. **每步超时 60s + 总预算 4 步**，超时降级为"先把第一步做了"

### 3.4 验收标准

- 30 条既有语料 **不得低于 30/30**
- 上表 6 条复合请求，至少 4 条能拆出 ≥2 个动作
- 单句命令的 P50 延迟不超过 1 秒
- 所有花钱动作仍然 100% 经过确认卡

## 四点五、实现结果（2026-10-27）

按方案 B 落地了第一版工具循环，保留规则快速通道与确认门：

- `backend/app/agent/planner.py`：复合句判定、规则分句、模型规划（仅复合/模糊时调用）
- `node_decide` 增加复合分支 → `prepare_multi`（一次确认列出全部步骤）→ `dispatch_multi`
- 依赖前一步产物的动作（如"先出图再做视频"）会被标记并延后，不会拿空首帧硬跑
- 多步执行按意图分派到各自的 prepare 节点（`_prepare_for`）

实测：

```
多步拆分 4/4        第2张改亮后导出 / 配乐+片头 / 字幕+导出 / 出图+视频
连续执行 通过        配乐 + 片头 两次写入都生效
30 条语料 30/30      未回退
无 GPU 回归 12/12
```

期间修掉两个真问题：

1. `route_after_confirm` 新增 `dispatch_multi` 后映射表漏了它（自检脚本抓不到跨函数新增，
   已补上并纳入检查）
2. 产物编号按 `created_at` 排序，同秒插入时顺序不稳定 → `#1 #2` 会漂移；改为
   `(created_at, rowid)` 复合排序

## 三点五、不加 deepagents，先补「认知短板」（2026-10-27）

结论：**不引入 deepagents**。理由是这个产品不是通用 agent，动作空间就那十来个，
多一层规划框架带来的复杂度（依赖新、调试链变长、单次思考 2 分钟×N 步）大于收益。

改为先补两件事：

1. **解释型问答**（新增 `explain` 节点）
   - 触发：疑问句 + 「区别/哪个/怎么选/优缺点」
   - 事实来源：能力卡的 `name/desc/fields`，模型只允许基于这些回答
   - 实测：问「文生视频和图生视频有什么区别」能说出「多了一个首帧输入」；
     问「九图系列」能说出「最多 9 图 + 3 段参考音频」
2. **工具说明书化**
   - `PLAN_SYSTEM` 里每个工具补「什么时候用」，并给两个 few-shot 例子
   - 明确「能一步完成就不要拆」

回归：语料 30/30、多步 4/4、无 GPU 12/12、路由自检通过。

## 四、结论

- Step 1 已让助手"知道在说哪一张"，30/30
- 当前瓶颈是**动作空间单选**，规则继续加是负收益
- Step 2 采用 **B（工具循环 + 保留确认门 + 规则快速通道）**
- deepagents（C）暂不引入，等 B 上线后用同一套语料复测再决定

## 五、Step 1 收尾时发现的一个真 bug（已修）

`route_after_prepare` 新增了 `quick_reply` 返回值，但 `prepare` 这一条条件边的映射表漏了它：

```python
graph.add_conditional_edges("prepare", route_after_prepare,
                            {"chat": "chat", "confirm": "confirm"})   # 少了 quick_reply
```

后果：ComfyUI 连不上时，`node_prepare` 会返回 `intent=chat` 的提示，路由却没有对应的边，
直接把整轮打成 `failed: 'quick_reply'`——用户看到的是「出错了：'quick_reply'」。

修掉后同样场景的回复变成：

```
ComfyUI 现在连不上（TimeoutError），先去看服务管家把它启起来，再让我干活。
```

这类「新增路由返回值但漏改映射」的问题，靠人盯很容易漏。Step 2 引入工具循环前，
建议加一条静态自检：`route_after_*` 的所有返回值必须出现在对应 `add_conditional_edges` 的映射里。
