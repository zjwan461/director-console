# Agent 助手 — 设计稿

> 目标：在「创作台」前面加一个**纯自然语言**的入口，用户用聊天的方式完成「生成图片 / 生成视频 / 查素材 / 建项目 / 出片」，并且能看懂系统正在做什么。
>
> 状态：设计评审中，未开始实现。

---

## 1. 定位与命名

| 项目 | 结论 |
|---|---|
| Tab 位置 | 最前面，`创作台` 之前 |
| 候选名 | **导演助手**（推荐）/ AI 导演 / 共创台 |
| 一句话 | 「说人话就能出片」——不选卡片、不填参数，聊着就把活干了 |

为什么不叫「AI 聊天」：这个页面的价值不是聊天，而是**替用户操作整套流水线**。名字要体现"它在干活"。

## 2. 交互设计

### 2.1 页面结构

```
┌─────────────────────────────┬──────────────────┐
│  对话流（可滚动）             │  画布（右栏）      │
│                             │                  │
│  [用户] 一只黑猫在雪地里走    │  当前任务         │
│  [助手] 明白了，我这样理解…   │  ┌────────────┐  │
│  [工具] 检查模型 ✓           │  │ 生成中 62%  │  │
│  [助手] 需要确认：1080p…      │  └────────────┘  │
│         [开始生成] [改参数]   │  产物             │
│  [产物] 视频卡片 ▶            │  缩略图 / 视频     │
├─────────────────────────────┴──────────────────┤
│ [📎 参考图]  说点什么…                    [发送] │
└────────────────────────────────────────────────┘
```

- **左栏对话**是主视图，消息里嵌工具进度和产物卡片
- **右栏画布**持续显示"现在在干嘛 + 最近产物"，不用往上翻
- 右栏可折叠，窄屏时变成按钮

### 2.2 消息类型

| 类型 | 内容 | 交互 |
|---|---|---|
| 用户文本 | 纯文字 | — |
| 用户图片 | 参考图（多模态） | 可放大 |
| 助手文本 | 流式输出 | Markdown |
| **工具卡** | 工具名 + 参数 + 状态（运行中/成功/失败） | 可展开看详情 |
| **确认卡** | 将要执行的高成本操作 + 预估耗时 | [执行] [改一下] [取消] |
| **产物卡** | 图片/视频/项目/镜头 | 预览、下载、**跳到对应页面** |
| 错误卡 | 失败原因 + 可操作建议 | [重试] [看日志] |

### 2.3 三个关键交互约定

1. **一次只问一个关键问题**
   参数不全时，最多追问 1~2 个（例如"多长？默认 5 秒"），其余用项目默认值，并在确认卡里列出来让用户改。

2. **高成本操作必须确认**
   视频生成（几分钟、占显存）、导出成片（几分钟）→ 弹确认卡；图片生成、查素材、建项目 → 直接做。
   阈值可以在设置里调（"总是确认 / 超过 1 分钟才确认 / 从不确认"）。

3. **刷新不丢**
   长任务跑着的时候刷新页面、切 tab，回来还能看到进度和结果（沿用现有 `renders`/`jobs` 的恢复思路）。

### 2.4 上下文与引用

- 自动带上**当前项目**（如果有）：风格、已有镜头、时长
- 支持 `@` 引用素材：`@黑猫.png` → 作为首帧
- 支持"上一张图""刚才那个视频"这类指代（会话内产物 ID 映射）
- 多轮改稿：`"再慢一点"` → 只改 `duration`/`speed`，其余沿用

## 3. 核心矛盾：这不是一个"聊天框 + 函数调用"

普通 agent 的模型是「一问一答，几秒结束」。但这里：

| 现实约束 | 后果 |
|---|---|
| 视频生成 2~10 分钟 | 不能用一次 HTTP 请求同步等 |
| 生成要花钱/占显存 | 需要人工确认门 |
| 用户会中途刷新/关浏览器 | 状态必须落库，能续跑 |
| 要跨多轮、跨页面 | 会话状态不能只在前端内存 |
| 失败要能重试/换参数 | 需要显式的状态与重放能力 |

**结论：真正的难点不是"调模型"，而是"长任务编排 + 可恢复 + 人在环"。**

## 4. 框架选型

### 4.1 三个候选的实质关系

```
LangChain 1.x
├── create_agent()        ← 一行建一个 ReAct agent（底层就是 LangGraph）
├── LangGraph             ← 显式状态机：节点、边、interrupt、checkpointer、stream
└── deepagents            ← 建在 LangGraph 上：planning 工具 + 子 agent + 虚拟文件系统
```

不是三选一，而是**三层**。deepagents 也是 LangGraph 的一个应用。

### 4.2 对比

| 维度 | `create_agent`（普通 agent） | **LangGraph（显式图）** | deepagents |
|---|---|---|---|
| 上手成本 | 最低 | 中 | 低（但黑盒） |
| 长任务（分钟级） | 差：一次 run 内阻塞 | **好**：拆分节点 + 外部事件驱动 | 中 |
| 人工确认（interrupt） | 勉强（需包一层） | **原生 `interrupt()` + `Command(resume)`** | 有，但受其抽象限制 |
| 刷新恢复 | 无 | **checkpointer 落库即可** | 有（依赖其 thread 存储） |
| 流式输出 | 好 | **好（`astream_events`）** | 好 |
| 可控性/可调试 | 中（黑盒循环） | **高**：每个节点可打日志、可单测 | 低 |
| 多步规划 | 靠模型自觉 | 自己画 | **内置 planning 工具** |
| 子任务并发 | 无 | 自己实现（可 `Send` 并行） | **内置 subagents** |
| 依赖体积 | 小 | 小（langgraph + langchain-core） | 中大 |

### 4.3 结论：**用 LangGraph 显式图，不用 deepagents**

理由按重要性排：

1. **我们的流程是"确定性为主、模型决策为辅"**
   生成视频的步骤是固定的：查模型 → 确认 → 提交 → 轮询 → 落库 → 汇报。这不是"让模型自由发挥"能做得更稳的场景。显式图能把每步做成可观测、可重试的节点。

2. **interrupt + checkpointer 是刚需**
   确认门和刷新恢复都直接对应 LangGraph 的两个原生能力。用 `create_agent` 要自己造这两样，等于重写半个 LangGraph。

3. **长任务必须"出图"**
   生成是外部异步任务（ComfyUI 队列）。图里应该是 `dispatch_node` → （退出，等外部事件）→ `resume_node`，而不是在一个 agent run 里 `while poll`。这只有显式图好写。

4. **deepagents 的能力我们用不上（暂时）**
   它的卖点是"自主规划 + 子 agent + 文件系统"，适合开放式长任务（写代码、做研究）。我们的任务是**收敛的**（出图/出片），过度自主反而不可控、更难调试。
   如果以后要做"整片自动编排"（一次给 30 镜排片），可以**把 deepagents 作为某一个节点内部**使用，外层仍然是我们的图。

5. **依赖轻**
   只装 `langgraph` + `langchain-core` + `langchain-openai`（走现成的 OpenAI 兼容接口），不装整个 `langchain`。

### 4.4 落地版本

```txt
langgraph>=1.0,<2
langchain-core>=1.0,<2
langchain-openai>=1.0,<2
```

> 你项目里用过 1.3.18，和我们需要的 API（`StateGraph` / `interrupt` / `MemorySaver`+SQLite checkpointer / `astream_events`）一致，可以直接沿用经验。

## 5. 架构

```
浏览器
  │  POST /api/agent/threads/{id}/messages   (用户输入，含图片)
  │  GET  /api/agent/threads/{id}/stream     (SSE，复用 prompt_stream 的模式)
  ▼
FastAPI
  ├── AgentRuntime（LangGraph 编译图 + SQLite checkpointer）
  │     ├── 节点：understand → plan → call_tool → need_confirm → dispatch → wait → report
  │     └── 工具：下方清单，全部调用**现有内部函数**，不走 HTTP 自调用
  ├── JobRunner / RenderRunner（已有，继续负责真正的生成）
  └── SQLite（新增 agent_* 表；checkpointer 也落这里）
        │
        ▼
     ComfyUI (192.168.56.66:39009)
```

**工具实现方式**：直接调用 `app.main` / `app.store` / `app.ai_script` 里的函数，不绕一圈 HTTP。这样工具层和 REST 层共享逻辑，也避免自己调自己。

        │   intake     │  收消息、解析附件、取项目上下文
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │  classify    │  闲聊 / 查信息 / 生成 / 改稿 / 编排
        └──────┬───────┘
     ┌─────────┼──────────────┬───────────────┐
     ▼         ▼              ▼               ▼
  ┌──────┐ ┌────────┐   ┌──────────┐   ┌──────────┐
  │ chat │ │ lookup │   │  build   │   │  revise  │
  └──────┘ └────────┘   │  params  │   └────┬─────┘
                        └────┬─────┘        │
                             ▼              │
                     ┌───────────────┐      │
                     │ need_confirm? │◄─────┘
                     └───┬───────┬───┘
                   是     │       │ 否
                          ▼       ▼
                   ┌──────────┐ ┌────────────┐
                   │ interrupt│ │ dispatch   │ 提交 ComfyUI 任务
                   └────┬─────┘ └─────┬──────┘
                        │ resume      ▼
                        └──────► ┌────────────┐
                                 │ wait_job   │ 外部事件驱动，不在图里阻塞

要点：

- `wait_job` 不轮询阻塞；由 JobRunner 完成后 `resume`（或前端轮询 + 后端标记）

- 每步都写 checkpoint，刷新后从最后一步继续

## 7. 工具清单（映射到现有能力）

| 工具 | 作用 | 后端来源 | 需确认 | 典型耗时 |
|---|---|---|---|---|
| `list_presets` | 列出可用能力卡 | `GET /api/presets` | 否 | 瞬时 |
| `check_models` | 查模型是否齐 | `model_check.check_models` | 否 | 1~3s |
| `list_assets` | 找素材（含标签筛选） | `store.search_assets` | 否 | 瞬时 |
| `describe_image` | 看图（多模态） | `ai_script` + vision_model | 否 | 3~8s |
| `make_image` | 文生图/图生图 | `POST /api/jobs`（图片卡） | 否 | 20~60s |
| `make_video` | 文生/图生/参考生视频 | `POST /api/jobs`（视频卡） | **是** | 2~10min |
| `job_status` | 查任务 | `store.get_job` | 否 | 瞬时 |
| `cancel_job` | 取消 | 同上 | 否 | 瞬时 |
| `save_as_shot` | 产物存为镜头 | `POST /api/jobs/{id}/save-as-shot` | 否 | 瞬时 |
| `create_project` | 建项目 | `store.create_project` | 否 | 瞬时 |
| `write_script` | 生成字幕/旁白 | `ai_script.generate` | 否 | 3~10s |
| `plan_bgm` | 按段落配乐 | `ai_bgm_plan` | 否 | 1~2s |
| `render_film` | 导出成片 | `create_render` | **是** | 1~5min |
| `probe_frames` | 抽帧看效果 | `/api/shots/{id}/frames` | 否 | 1~2s |

**工具设计原则**

1. **一个工具只做一件事**，不要 `do_everything(action=...)`
2. **返回结构化 JSON**（含 `ref_id`），模型据此引用产物
3. **失败要带可操作信息**：不是 `error: failed`，而是 `{ok:false, reason:"model_missing", hint:"缺 xxx.safetensors，可点这里下载"}`
4. **耗时 >30s 的工具**必须走"提交 + 轮询"两段式，不能同步返回

## 8. 数据模型（新增 4 张表）

```sql
agent_threads(id, title, project_id, created_at, updated_at, archived)
agent_messages(id, thread_id, role, content, parts_json, run_id, created_at)
agent_runs(id, thread_id, status, node, state_json, error, started_at, finished_at)
agent_artifacts(id, run_id, kind, ref_id, url, meta_json, created_at)
```

- `parts_json` 存多模态片段（文本/图片/工具卡/产物卡），前端直接渲染
- LangGraph 的 checkpointer 用 `AsyncSqliteSaver`，同一个 db 文件、独立表
- 一个 thread 可绑定 `project_id`，切换项目时另起会话（或提示"新项目，开新对话？"）

## 9. 流式协议（SSE）

事件按顺序推送，前端按 `run_id` 聚合：

```jsonl
{"t":"run_start","run_id":"run_x","thread_id":"th_1"}
{"t":"message","role":"assistant","delta":"好的，我来"}
{"t":"tool_call","id":"c1","name":"make_video","args":{...}}
{"t":"tool_result","id":"c1","ok":true,"data":{"job_id":"job_x"}}
{"t":"need_confirm","id":"a1","summary":"生成 5 秒 1080p 视频","eta":"约 4 分钟","actions":["run","edit","cancel"]}
{"t":"artifact","kind":"video","ref_id":"job_x","url":"/media/outputs/..."}
{"t":"run_end","run_id":"run_x","status":"ok"}
```

- 复用 `prompt_stream.py` 的 `StreamingResponse(media_type="text/event-stream")` 写法
- 断线重连：前端带 `Last-Event-ID` 或 `?after=<seq>`，从 `agent_messages` 补历史

## 10. 上下文工程

**系统提示词结构（分块，便于维护）**

```
1. 角色：你是导演台的助手，替用户操作视频/图片生成流水线
2. 当前环境：ComfyUI 在线/离线、可用卡片列表（摘要）、缺失模型（摘要）
3. 当前项目：id、名称、已有镜头（标题+时长）、风格
4. 工具使用规则：何时确认、如何追问、禁止编造 job_id
5. 输出风格：短句、先结论后细节、产物用卡片不用纯文本
```

**上下文预算**

- 系统提示 + 环境快照：≤ 2k tokens（卡片列表只给 id+名称+一句话）
- 历史消息：滑动窗口 20 条 + 更早的摘要（每 10 轮压一次）
- 图片：只保留最近 3 张的缩略描述，原图存磁盘

**多模态**

- 用户上传图 → 存资产 → 传给 vision 模型做描述 → 描述进上下文（原图给生成用）
- 生成完成 → 抽首帧 → 让 vision 模型自查"是否符合描述" → 不符则提示重试

## 11. 成本与安全

| 控制 | 做法 |
|---|---|
| 单次 run 步数上限 | 12 步（超出强制收尾并汇报） |
| 单线程日生成数上限 | 50 次（可配置） |
| 并发生成 | 同时最多 1 个视频任务 |
| 确认门 | 视频/导出必须确认；可在设置里放宽 |
| 幻觉防护 | `job_id` / `asset_id` 只能来自工具返回值，系统提示明确禁止编造 |
| 危险操作 | 删除项目/素材 → 一律确认，且默认不提供该工具 |

## 12. 失败与降级

| 场景 | 行为 |
|---|---|
| ComfyUI 离线 | 提前识别，直接回复"ComfyUI 未连接，要我先启动吗？"+ 按钮 |
| 模型缺失 | 复用 `model_check` 的 `reason`（missing/node/folder），给下载命令 |
| 生成失败 | 展示原始错误摘要 + [重试] [换参数] [换卡片] |
| 超时 | 提示"已超过 10 分钟，可能显存不足"，附取消按钮 |
| 服务重启 | run 标记为 `interrupted`，下次进入提示"上次中断在第 3 步，继续？" |

## 13. 与现有页面的关系

- 产物卡片点击 → 跳转到 **成片 / 资产 / 剪辑** 对应条目（带 `?project=&shot=`）
- "存为镜头" → 直接进项目，用户可去剪辑页继续
- 助手对话产生的项目/镜头，和手动创建的**没有区别**（同一套表）
- 剪辑页的 AI 按钮保持现状（批量、可预览），助手适合"从零到有"的探索

## 15. 待确认的设计决策

1. **Tab 名字**：导演助手 / AI 导演 / 共创台？
2. **确认门的粒度**：视频和导出都确认（稳妥）vs 只有导出确认（流畅）？
3. **是否绑定项目**：全局会话（跨项目，靠切换上下文）vs 一会话一项目（清晰但碎）？
4. **工具范围 M1**：只放"图片生成 + 查素材"够不够验证？
5. **是否要"看回放"**：把 agent 的每一步决策展示给用户（调试友好，但可能显得啰嗦）
